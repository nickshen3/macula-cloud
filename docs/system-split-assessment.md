# P3-4 System 服务拆分评估报告

> 状态：评估完成，**结论：现阶段不拆分** ｜ 日期：2026-08-15 ｜ 关联：IMPROVEMENT-PLAN.md P3-4

## 1. 评估对象与方法

对象：`macula-cloud-system`（用户/角色/菜单/部门/租户/字典/日志/权限/应用，10 个 Controller）。
方法：域内聚度 × 调用耦合 × 团队规模适配 × 运维成本 四维测算。

## 2. 现状量化

| 维度 | 数据 |
|------|------|
| 代码规模 | 90 个 Java 文件，约 6.6k 行（中小规模单体） |
| 业务域 | 10 个 Controller：User/Role/Menu/Dept/Tenant/DictType/DictItem/Log/Permission/Application |
| 对外 API（Feign） | system-api 模块仅 2 个客户端：UserFeignClient（IAM 登录链路用）、MenuFeignClient（菜单路由） |
| 跨域调用方 | IAM（用户认证查询）、网关（鉴权introspection 经 IAM 间接）、前端管理台 |
| 数据库 | 单库 `macula-system`，表间外键/联查（用户-角色-菜单-租户 join 频繁，见 SysUser 查询 SQL） |

## 3. 收益测算（拆分能带来什么）

| 收益 | 现实评估 |
|------|---------|
| 独立伸缩 | 日志写入是唯一可能高负载域；其余域 QPS 极低（管理台后端）。**收益≈0** |
| 团队并行开发 | 当前 1 个小团队维护全栈；按域拆分引入跨服务协作成本 > 并行收益。**负收益** |
| 故障隔离 | 管理台整站可用性要求一致（用户挂了菜单也没意义）；拆分不改变用户感知。**收益≈0** |
| 数据自治 | 用户-角色-租户强关联联查（登录 SQL 一次 join 4 表）；拆库后要么冗余同步要么跨服务查询，**成本显著** |
| 部署灵活性 | 全量部署 3 服务已轻量；拆到 5-8 服务徒增 Nacos/监控/网关路由维护面。**负收益** |

## 4. 成本与风险（若现在拆）

1. **登录链路重构**：SysUser 查询 SQL 跨 User/Role/Tenant 三域，拆分后 IAM 认证需 3 次 Feign + 事务一致性处理（当前 1 次 SQL）。登录是系统最热路径，P1-2 的 IT 需全部重写。
2. **分布式事务**：用户-角色授权变更当前单库事务；拆分引入 Seata 正式使用（当前 seata 模块空转）或最终一致改造。
3. **运维面翻倍**：+N 个 Java 进程 ×（Nacos 注册/Prometheus 指标/日志/CI/部署脚本）。
4. **回不去了**：拆分后合并成本极高，属近不可逆决策。

## 5. 触发条件（何时重评）

满足**任一**条件时重开评估：

- [ ] system 单服务代码量 > 20k 行，或 > 3 个特性团队同时改此仓库（merge 冲突高频）
- [ ] 日志/审计域独立高负载（写入 > 1k TPS），拖累其他域
- [ ] 租户级物理隔离合规要求出现（金融/政务场景）
- [ ] 组织架构调整为独立基础平台团队 + 业务团队

## 6. 替代优化（不拆分下缓解单体痛点的低成本动作）

| 痛点 | 动作 | 成本 |
|------|------|------|
| 日志表膨胀拖慢主库 | 日志表按月分区 + 定期归档（纯 DBA 操作） | 0.5 人日 |
| 域边界腐化 | 包结构按域收敛（controller/service/entity 各域子包），ArchUnit 测试守护跨域 import | 1 人日 |
| 大表联查性能 | 慢查询监控 + 索引审计（已有 actuator/prometheus 基础） | 0.5 人日 |

## 7. 结论

**现阶段（1 个小团队、管理台场景、单库联查密集）不拆分**。执行 §6 的三个低成本动作守住边界；按 §5 触发条件每年复核一次。
